SCHED_FIFO（先进先出）和 SCHED_RR（时间片轮转）是 Linux 操作系统内核中用于实时进程（Real-Time Process）的两种核心调度策略。
在机器人运动控制、自动驾驶、音视频采集等对时间极其敏感的场景中，普通的 Linux 调度器（CFS，完全公平调度）无法保证关键代码在规定微秒内得到执行。此时就需要将核心进程设为 SCHED_FIFO 或 SCHED_RR，赋予它们绝对的 CPU 抢占权。

一、 核心前提：实时优先级机制

在理解这两种策略之前，需要明确 Linux 调度器的基本规则：
• 优先级范围： 实时进程的静态优先级范围是 1 到 99（数字越大，优先级越高）。所有普通进程（SCHED_OTHER）的静态优先级都是 0。
• 绝对抢占： 只要有一个优先级为 1~99 的实时进程处于可运行（Runnable）状态，它就会立刻剥夺普通进程的 CPU 使用权。
• 高抢低： 优先级高的实时进程（如优先级 80）会立刻抢占优先级低的实时进程（如优先级 50）。
SCHED_FIFO 和 SCHED_RR 的核心区别，在于当多个“相同优先级”的实时进程同时抢占同一个 CPU 核心时，它们如何分配时间。

二、 SCHED_FIFO（First-In, First-Out，先进先出）

SCHED_FIFO 是一种没有时间片限制的霸道调度策略。
• 运行机制： 当一个 SCHED_FIFO 进程拿到 CPU 后，它会一直运行下去，直到以下三种情况之一发生才会交出 CPU：
	1. 主动放弃： 进程运行结束，或者自己调用了 sleep()、等待互斥锁、等待 I/O 数据而进入阻塞状态。
	2. 被更高优先级抢占： 出现了一个优先级数字更大的实时进程。
	3. 主动让出： 进程显式调用了 sched_yield() 函数，把自己排到同优先级队列的末尾。
• 同优先级处理： 如果有多个相同优先级的 SCHED_FIFO 进程，先进入就绪队列的进程会一直运行，排在后面的同级进程必须死等，直到前面的进程阻塞或退出。
• 适用场景： 机器人最核心的 1kHz 电机控制环、紧急避障响应线程。这类任务单次计算时间极短且确定，要求一旦触发就必须一口气执行完，绝对不能中途被打断。

三、 SCHED_RR（Round-Robin，时间片轮转）

SCHED_RR 是 SCHED_FIFO 的改良版，引入了时间片（Time Quantum）的概念，防止某个进程把同级兄弟“饿死”。
• 运行机制： 与 SCHED_FIFO 类似，高优先级依然会抢占低优先级。但对于相同优先级的多个 SCHED_RR 进程，内核会给每个进程分配一个固定的时间片（通常为 100 毫秒左右）。
• 同优先级处理： 当进程 A 用完了自己的时间片后，即使它还在运行，内核也会强制暂停它，把它放到同优先级队列的末尾，然后让队列里的下一个同级进程 B 运行。如果队列里只有一个该优先级的进程，它会连续不断地获得时间片继续运行。
• 适用场景： 多个同等重要、且需要持续占用 CPU 进行计算的并行任务，例如双臂协同中的两路独立传感器数据预处理，需要保证两者都能公平地获得算力。

四、 核心对比总结


|对比维度	|SCHED_FIFO（先进先出）	|SCHED_RR（时间片轮转）|	普通调度（SCHED_OTHER）|
|---|---|---|---|
|优先级范围|	1 ~ 99（实时）|	1 ~ 99（实时）	|0（非实时，靠 Nice 值微调）|
|时间片限制|	无时间片，运行到阻塞或被抢占为止	|有固定时间片，用完排到同级队尾|	动态计算虚拟运行时间
|同优先级竞争|	先到先得，后者可能被饿死|	轮流执行，保证同级公平|	按权重公平分享 CPU
|潜在风险|	若代码出现死循环，会直接卡死整个系统|	若死循环，同级可轮转，但低级依然卡死|	不会卡死系统，内核有保护机制|


五、 工程实践中的安全防线（面试高频追问）

使用 SCHED_FIFO 或 SCHED_RR 是一把双刃剑。如果一个优先级为 99 的 SCHED_FIFO 进程写出了 while(1) 死循环，连系统的 SSH 终端和键盘中断进程（普通优先级）都抢不到 CPU，整台机器人会瞬间“假死”失控。
Linux 内核为此专门设置了一道全局安全阀（RT Throttling）：
• 通过 /proc/sys/kernel/sched_rt_period_us（默认 1000000 微秒，即 1 秒）和 /proc/sys/kernel/sched_rt_runtime_us（默认 950000 微秒，即 0.95 秒）两个参数控制。
• 这意味着系统默认规定：所有实时进程在每 1 秒内最多只能占用 0.95 秒的 CPU，必须强制留出 0.05 秒（5%） 给普通系统进程，确保运维人员在极端情况下依然能连上终端排查或杀死故障进程。
