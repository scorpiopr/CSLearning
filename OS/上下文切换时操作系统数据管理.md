## ❓ 问答题：进程上下文切换时，操作系统具体保存和恢复了哪些底层数据？
## 🎯 核心结论
进程上下文切换的本质，就是把前一个进程的运行环境安全地保存到内存中，然后把新进程先前保存的运行环境恢复到 CPU 寄存器中，让新进程无缝接着上一次的位置继续执行。
这些数据主要分为两大类：CPU 寄存器内容（硬件上下文）和内核管理数据（软件上下文）。
------------------------------
## 🗂️ 具体保存和恢复的数据清单
## 1. CPU 寄存器上下文（User/Kernel CPU Context）
这是最直接、最核心的数据。CPU 内的寄存器决定了当前程序执行到了哪一步、数据是什么。

* 程序计数器 (PC / IP)：存储下一条要执行的机器指令的内存地址。换言之，它记录了程序“执行到了哪一行代码”。
* 栈指针 (SP / ESP / RSP)：指向当前进程的栈顶。每个进程都有独立的函数调用栈，用来存放局部变量、函数参数和返回地址。
* 通用寄存器 (AX, BX, CX, DX 等)：存放当前正在参与运算的临时变量、计算结果。
* 状态寄存器 (Flags / EFLAGS)：存放条件判断的状态（如是否为零、是否溢出、正负号等）。
* 段寄存器 (CS, DS, SS 等)：用于内存寻址和权限控制。
* 高级寄存器：现代 CPU 还会保存浮点寄存器 (FPU) 和 向量/多媒体寄存器 (AVX/MMX/SSE)（仅在进程使用了它们时才保存）。

## 2. 内核管理上下文（OS PCB / Thread Info）
除了 CPU 内部的寄存器，操作系统内核还需要切换与该进程绑定的管理信息。

* 页表基址寄存器 (CR3 / PGD)：【进程切换的关键】
* 每个进程都有独立的虚拟内存空间。切换进程时，必须将 CR3 寄存器 指向新进程的页表（Page Table）首地址。
   * 注意：这会导致 CPU 的 TLB（页表缓存 / 快速地址转换缓存）失效。这是进程切换比线程切换开销大得多的核心原因！
* 进程控制块 (PCB / Linux 中的 task_struct)：
* 更新前一个进程的状态（从“运行”改为“就绪”或“阻塞”）。
   * 读取新进程的状态（改为“运行”）。
   * 切换进程的内核栈（Kernel Stack）。每个进程在内核态都有独立的内核栈。
* 文件描述符表 (File Descriptor Table)：切换当前进程打开的文件、Socket 连接等资源的映射表。
* 权限与凭证 (Credentials)：切换当前进程的运行权限（UID、GID 等）。

## 🔄 状态切换的具体流水线（以 Linux 为例）
当时间片耗尽或发生 I/O 阻塞时，切换过程如下：

   1. 陷入内核：触发时钟中断或系统调用，CPU 从用户态（User Mode）切换到内核态（Kernel Mode）。
   2. 保存用户态上下文：CPU 自动或内核手动将用户态的寄存器（PC, SP 等）压入该进程的内核栈中。
   3. 调用调度器：内核执行调度算法（如 CFS），选出下一个要运行的进程。
   4. 切换硬件上下文（switch_to 宏）：
   * 改变 CR3 寄存器，切换虚拟内存空间。
      * 将当前 CPU 的寄存器值存入当前进程 task_struct->thread 结构体中。
      * 将新进程先前保存的值载入 CPU 寄存器。
   5. 恢复并返回：新进程的内核栈弹出先前保存的用户态寄存器，CPU 返回用户态，新进程从上次中断的地方继续执行。

## ⚠️ 面试高频追问：进程切换 vs 线程切换
面试官通常会顺着这道题追问：“为什么进程切换比同一进程内的线程切换慢得多？”

* 相同点：线程切换同样需要保存和恢复 CPU 寄存器（PC, SP, 通用寄存器等）。
* 不同点：同一进程内的线程共享相同的虚拟内存空间（同一张页表）。因此，线程切换时不需要切换 CR3 寄存器，不需要刷新 TLB 缓存。而进程切换必须刷新 TLB，导致切换后新进程频繁发生 TLB Miss（缓存未命中），需要重新去内存里查页表，这带来了巨大的性能开销。
